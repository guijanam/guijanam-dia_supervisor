# 추첨 자동 실행 + 결과 문서 자동 게시 (설계안)

> **상태: 검토용 설계안 — 아직 구현하지 않았다.**
> 구현 여부를 결정하기 위한 문서다. 이 문서에 적힌 코드/컬럼은 현재 레포에 없다.

## 이 문서의 목적

관리자의 수동 개입을 줄이기 위해, **신청 마감일이 지나면 지근 추첨을 자동으로
실행하고 그 결과를 문서로 자동 게시**하는 기능을 검토한 결과를 남긴다.

결론부터: **가능하다.** 다만 이 앱에는 서버가 없어서 "아무도 접속하지 않아도
밤에 저절로" 는 새 인프라 없이는 불가능하다. 그래서 아래 설계는
**관리자가 앱에 접속한 시점에 1회 자동 실행**하는 방식을 택했다.

---

## 전제 — 신청 기간의 3단계 (현행 동작)

자동 추첨이 **어느 구간에 끼어드는지**가 이 설계의 전제이므로 먼저 정리한다.
사용자 화면은 `phase` 라는 3상태로 동작한다
([user-calendar.tsx:175-179](../components/user-calendar.tsx#L175-L179)).

아래 타임라인은 **신청을 받는 일정**이고, 그 신청이 **어느 분기를 대상으로
하는지는 별개**다(대상 분기는 보통 이 일정보다 한두 달 뒤에 시작된다 —
2절 참고). 예시 날짜는 3분기(7~9월)를 두 달 전에 받는 경우다.

```
        request_freeze_date              extra_request_deadline
        (예: 5/31)                        (예: 6/7)
        ※ 신청 대상은 7~9월 — 일정과 대상 분기는 다르다
             │                                 │
  open       │            closed / extra       │      closed
─────────────┼─────────────────────────────────┼──────────────────→
  전원        │  전원 잠김                       │  전원 잠김
  신청·삭제   │   └ 단, 탈락자에게만 열림(extra)  │
             │                                 │
             └─ 6/1 0시부터 즉시 잠김            │
                                                │
        ┌────────────────────────────────┐      │
        │ 이 구간에 관리자가 추첨을 실행    │      │
        │ → 탈락자(lottery_status='lost') │      │
        │   가 정해져야 extra 가 성립한다  │      │
        └────────────────────────────────┘   ← 자동화 대상
```

| 단계 | 조건 | 동작 |
|---|---|---|
| `open` | 마감일 이전 | 전원 신청·삭제 자유. **정원 초과 신청 허용** — 초과분을 추첨으로 거르는 것이 기존 운영이라 여기서 막으면 선착순이 된다 |
| `closed` | 마감일 경과, 추가 기간 아님 / 또는 추가 기간이지만 탈락 이력 없음 | 신청·삭제 모두 차단 |
| `extra` | 마감일 경과 + 추가 기간 내 + **그 분기에 `lottery_status='lost'` 보유** | 신청·삭제 다시 열림 |

**흔한 오해 세 가지 — 이 문서를 읽을 때 주의**

1. **"마감일 후 일주일 뒤에 추가 기간이 시작된다" 가 아니다.**
   마감 다음날 0시부터 **즉시 잠기고**, 추가 기간은 그 잠긴 구간 안에서
   탈락자에게만 열리는 것이다. 그리고 그사이에 **관리자가 추첨을 돌려야**
   탈락자가 정해진다. 추첨 전에는 `lost` 행이 없어 아무도 자격이 없으므로
   추가 기간이 열려 있어도 **전원 `closed`** 다.
   → **추첨이 늦어질수록 탈락자가 쓸 수 있는 기간이 줄어든다.**
   자동 추첨의 실질적 효용이 바로 여기에 있다.

2. **추가 기간에는 정원 제한이 새로 걸린다.**
   1차(`open`)와 달리 `extra` 에서는 정원이 찬 날에 신청할 수 없다
   ([user-calendar.tsx:181-199](../components/user-calendar.tsx#L181-L199)).
   이미 추첨으로 자리가 확정된 상태이기 때문이다. 탈락한 그 날짜에 다시
   신청하는 것도 막힌다(`countJigeunSlots` 가 `lost` 를 자리 비움으로
   세는 규칙의 귀결 — [schedule-utils.ts:118-134](../lib/schedule-utils.ts#L118-L134)).
   따라서 탈락자는 **빈 자리가 있는 다른 날짜로** 새로 신청해야 한다.

3. **탈락 건은 지워지지 않는다 — 화면에서 숨겨질 뿐이다.**
   DB 행은 `lottery_status='lost'` 인 채로 **그대로 남는다**. 추첨 탈락자
   목록과 추가 신청 자격의 **유일한 근거**라서 지울 수 없다
   ([migrations.sql:141-147](../supabase/migrations.sql#L141-L147)).
   대신 사용자 화면에서만 본인 신청내역·월 집계·본인 칩에서 빼고
   "추첨 탈락" 표시만 남긴다
   ([user-calendar.tsx:395-402](../components/user-calendar.tsx#L395-L402)) —
   남겨 두면 아직 자기 자리인 줄 알고 혼동하기 때문이다.

   그 결과 **사용자는 탈락 건을 삭제할 수 없다.** 탈락 행은 `specialMap` 에
   없어 `existing` 이 잡히지 않고, `remove()` 는 `if (!existing) return` 으로
   시작하므로 애초에 실행되지 않는다
   ([day-modal.tsx:138](../components/day-modal.tsx#L138)).

   그렇다면 추가 기간의 **삭제 허용**은 무엇을 위한 것인가 —
   **탈락하지 않고 살아 있는 다른 날짜의 신청**을 정리하기 위해서다.
   탈락으로 한 자리가 비면 분기 합계 24 가 어긋나므로, 남은 신청을 지우고
   다른 날로 다시 잡는 조정이 필요하다
   ([user-calendar.tsx:203-204](../components/user-calendar.tsx#L203-L204)).

> 관리자는 이 3단계를 모두 무시한다. 대리 등록 화면은
> `phase="open"` / `enforceJigeunCap={false}` 를 하드코딩한다
> ([admin-employee-calendar-view.tsx:604-611](../components/admin-employee-calendar-view.tsx#L604-L611)).

## 현재 상태 — 관리자가 지금 해야 하는 일

마감일이 지난 뒤 관리자는 세 가지를 순서대로 수동 처리한다.

1. **추첨 실행** — 관리자 캘린더에서 달을 넘겨 가며 정원 초과 날짜를 찾아
   `일괄 추첨` 버튼 클릭. 이 버튼은 **화면에 보이는 한 달**만 대상이므로
   분기를 처리하려면 세 번 반복해야 한다.
   ([admin-calendar.tsx:212-240](../components/admin-calendar.tsx#L212-L240),
   [admin-calendar.tsx:550-600](../components/admin-calendar.tsx#L550-L600))
2. **명단 확인** — `추첨 탈락자` 패널에서 분기별 탈락자 조회.
   ([lottery-losers-panel.tsx](../components/admin-panels/lottery-losers-panel.tsx))
3. **직원 통보** — 현재는 패널의 `tel:`/`sms:` 링크로 개별 연락하거나
   `추첨탈락자_{year}Q{quarter}.xlsx` 를 내려받아 따로 전달한다.
   추첨 결과가 `documents`/`announcements` 로 게시되는 경로는 **현재 전혀 없다**.

자동화 대상은 **1번과 3번**이다.

**왜 시급한가 — 관리자가 늦으면 직원이 손해를 본다.**
위 3단계는 단순히 번거로운 것이 아니라 **시간에 쫓기는 작업**이다. 앞의
타임라인에서 보듯 추첨이 끝나야 `extra` 가 성립하므로, 관리자가 추첨을
하루 늦게 돌리면 탈락자가 재신청할 수 있는 기간이 하루 줄어든다. 마감 후
며칠간 관리자가 바빴다면 탈락자는 남은 이틀 안에 빈 날짜를 찾아야 한다.

자동 추첨은 이 지연을 **관리자가 앱을 여는 시점**까지 당긴다. 결과 문서
게시까지 함께 도므로, 탈락자가 "내가 떨어졌다" 를 알게 되는 시점도 같이
앞당겨진다(현재는 관리자의 개별 연락을 기다려야 한다).

## 핵심 제약 — 이 앱에는 서버가 없다

설계 선택지를 좌우하는 가장 중요한 사실이다.

| 항목 | 현재 상태 |
|---|---|
| API 라우트 | **없음** — `app/` 에는 `layout.tsx`, `page.tsx`, `manifest.ts`, `globals.css`, `icon.png` 뿐 |
| Server Action | **없음** — `"use server"` 0건 |
| 모든 컴포넌트 | `"use client"` |
| Supabase 접근 | anon 키 브라우저 클라이언트 1개 ([lib/supabase.ts](../lib/supabase.ts), 6줄) |
| `service_role` 키 | **금지** — [.env.example:18](../.env.example#L18), [multi-depot-deployment.md:418-419](./multi-depot-deployment.md#L418-L419) 에 "만들지도, 넣지도 않는다" 명시 |
| 스케줄러 (pg_cron / Vercel Cron / Edge Function) | **없음** |

특히 **마감일은 서버가 관찰하지 않는다.** `request_freeze_date` 는 오직
브라우저에서 `today > freeze_date` 로 비교될 뿐이다
([user-calendar.tsx:122-127](../components/user-calendar.tsx#L122-L127)).
DB 레벨 강제도 없다 — 마이그레이션 주석이 이를 명시하고 있다.

즉 "마감일이 지나면 저절로" 를 구현하려면 **아무도 접속하지 않아도 시각을
지켜보는 무언가**를 새로 만들어야 한다.

### 선택지 비교

| 방식 | 관리자 개입 | 비용 |
|---|---|---|
| **A. 관리자 접속 시 자동 실행** ← **채택** | 앱 열기 1회 | 없음. 새 키·새 인프라 불필요, 기존 보안 설계 유지 |
| B. Supabase pg_cron | 0 | 추첨 로직(Fisher-Yates, 정원 계산)을 SQL 로 **재구현**해야 함. 승무소별 프로젝트마다 마이그레이션 적용 |
| C. Vercel Cron + Route Handler | 0 | 기존 TypeScript 로직 재사용 가능하나 `service_role` 키 도입 논쟁. Hobby 플랜은 하루 1회 제한 |

**A 를 택한 이유**: 사용자 신청은 마감일에 이미 차단되므로, 관리자가 하루 이틀
늦게 접속해도 실무상 공백이 없다. 반면 B·C 는 새 인프라와 보안 원칙 변경을
요구한다. 개입을 "3단계 수동 작업" 에서 "앱 열기 1회" 로 줄이는 것만으로
목적의 대부분이 달성된다.

**A 의 한계 (명시)**: 관리자가 앱을 열기 전까지 실행되지 않는다. 만약
"관리자가 며칠 접속하지 않아도 반드시 그날 밤 실행" 이 요건이라면 B 가
필요하며, 그것은 별도 작업이다.

## 설계

### 1. 상태 관리 — `app_settings` 에 컬럼 2개 추가

자동 실행이 **딱 한 번만** 돌게 하는 멱등성 장치만 있으면 된다.
대상 분기는 기존 `extra_request_year` / `extra_request_quarter` 를 그대로
쓰므로 새 컬럼이 필요 없다(2절 참고).

```sql
alter table public.app_settings
  add column if not exists auto_lottery_enabled boolean not null default false;
alter table public.app_settings
  add column if not exists auto_lottery_done_for date;
```

- `auto_lottery_enabled` — 관리자가 설정에서 켜야만 동작한다.
  **기본값 `false` 가 중요하다**: 기존 배포가 코드 업데이트만으로 갑자기
  추첨을 돌려 버리면 안 된다.
- `auto_lottery_done_for` — 자동 실행을 마친 `request_freeze_date` 값.
  이 값이 현재 `request_freeze_date` 와 같으면 재실행하지 않는다.
  관리자가 다음 분기 마감일을 새로 잡으면 값이 달라지므로 자연히 다시 돈다.

[supabase/migrations.sql](../supabase/migrations.sql) 끝에 새 섹션으로 추가한다
(기존 파일이 `alter table ... add column if not exists` 누적 방식이므로 동일 관례).
**승무소별 Supabase 프로젝트마다 적용해야 한다** —
[multi-depot-deployment.md](./multi-depot-deployment.md) 의 마이그레이션 체크리스트 대상.

### 2. 실행 범위 — 어느 달을 추첨하는가

기존 `일괄 추첨` 은 화면에 보이는 한 달만 대상으로 한다. 자동 실행은 사람이
달을 넘겨 줄 수 없으므로 **분기 전체**를 대상으로 한다.
`quarterRange()` / `quarterMonths()` ([lib/quarter.ts](../lib/quarter.ts)) 재사용.

**대상 분기 판정 — 마감일에서 추론하면 안 된다.**

**마감일과 추가 신청일은 "언제 신청을 받고 닫는가" 라는 일정일 뿐,
"어느 분기를 대상으로 하는가" 와는 별개의 정보다.**

관행상 신청은 **대상 분기가 시작되기 한두 달 전**에 받는다. 몇 달 전인지는
분기마다 사정에 따라 다르다 — 고정된 규칙이 아니다. 확실한 것은 **마감일이
대상 분기보다 항상 앞선 다른 분기에 속한다**는 것뿐이다.

```
대상: 3분기(7~9월)
  ├─ 두 달 전에 받으면 → 마감일 5월 → 마감일이 속한 분기 = 2분기
  └─ 한 달 전에 받으면 → 마감일 6월 → 마감일이 속한 분기 = 2분기
                                        실제 대상 분기   = 3분기

대상: 4분기(10~12월)
  ├─ 두 달 전 → 마감일 8월 → 3분기
  └─ 한 달 전 → 마감일 9월 → 3분기
```

그래서 어떤 산식도 통하지 않는다. "마감일이 속한 분기" 는 항상 틀리고,
"다음 분기" 는 우연히 맞을 때가 있을 뿐 마감일이 분기 경계 근처로 움직이면
바로 어긋난다. **오프셋을 몇 달로 잡든 마찬가지다** — 그 오프셋 자체가
분기마다 달라지기 때문이다.

추가 신청일도 같다. 마감일 뒤 며칠~일주일 뒤에 잡히는 **일정**일 뿐이라
대상 분기와 무관하다.

따라서 **대상 분기는 계산하지 않고 관리자에게서 직접 받는다.**

이는 이 레포가 이미 학습한 교훈이기도 하다.
[migrations.sql:578-580](../supabase/migrations.sql#L578-L580) 이 `extra_request_*`
컬럼을 두면서 같은 이유를 적어 두었다:

> `extra_request_year` / `extra_request_quarter`: 24 합계를 계산할 대상 분기.
> **마감일에서 추론하지 않고** 관리자가 설정 화면에서 명시적으로 지정한다
> (예: 3분기 검증 중에 마감일을 4분기 첫날로 잡는 경우를 위해).

따라서 대상 분기는 **관리자가 명시한 값만 사용한다.** 문제는 그 값을 어디에
두느냐다.

#### 기존 `extra_request_year` / `extra_request_quarter` 를 그대로 쓴다

이 값은 **이미 관리자가 대상 분기를 명시적으로 지정해 둔 자리**다. 자동
추첨에 필요한 정보와 정확히 같으므로 새 컬럼을 만들지 않고 이 값을 쓴다.

이 선택의 이점이 크다 — 새 컬럼도, 값 이관 마이그레이션도, 사용자 화면
(`user-calendar.tsx`) 수정도 **전부 불필요**하다. 자동 추첨 기능이 기존
동작에 손대지 않고 얹히는 형태가 된다.

**단, 세 값 묶음 검증은 완화해야 한다.**

현재 UI 는 추가 신청일·연도·분기 세 값을 **함께 채우거나 함께 비우도록**
강제한다([jigeun-cap-settings.tsx:177-198](../components/jigeun-cap-settings.tsx#L177-L198)):

```ts
if (draftExtraDeadline) {
  if (!extraYearNum || !extraQuarterNum) → 에러
} else if (extraYearNum || extraQuarterNum) {
  → "추가 신청일을 비우려면 년·분기도 함께 비우세요"   // ← 이 방향을 푼다
}
```

이대로면 **추가 신청 기간을 운영하지 않는 분기**에 연도·분기만 남길 수 없어,
자동 추첨을 쓰려고 쓰지도 않을 추가 신청일을 억지로 넣어야 한다.

따라서 **역방향 검증만 제거**한다:

- **유지** — 추가 신청일이 있으면 연도·분기도 있어야 한다(판정에 필요하므로).
- **유지** — 추가 신청일은 마감일보다 뒤여야 한다.
- **제거** — "추가 신청일을 비우려면 연도·분기도 비워라".
  연도·분기는 **단독으로 남을 수 있다.**

저장 시 `extra_request_year` / `extra_request_quarter` 를
`extra_request_deadline` 유무와 무관하게 기록하도록 바꾼다(현재는 날짜가
비면 함께 NULL 로 되돌린다 — [jigeun-cap-settings.tsx:224-226](../components/jigeun-cap-settings.tsx#L224-L226)).

이에 맞춰 입력란의 의미를 화면에서 분명히 한다. 연도·분기는 추가 신청일의
하위 항목이 아니라 **그 분기 전체의 대상 지정**임을 설명문으로 밝힌다.

```
신청 마감일  [2026-05-31]  [해제]

☐ 마감일이 지나면 추첨을 자동 실행하고 결과를 문서로 게시      ← 신설
   관리자가 앱에 접속한 시점에 1회 실행됩니다. 아래 '대상 분기'를
   추첨하며, 이미 추첨한 날짜는 건드리지 않습니다.
─────────────────────────────────────────────
대상 분기    [2026 년] [3분기 (7~9월) ▾]      ← 라벨 신설, 위치 이동
             추첨·추가 신청이 대상으로 하는 분기입니다.
             추가 신청을 운영하지 않아도 지정해 두면 자동 추첨이 동작합니다.

추가 신청일  [2026-06-30]  [해제]
             (설명문은 현행 유지 — "선택한 분기에서" 가 위 대상 분기를 가리킴)
```

연도·분기 입력을 추가 신청일 **위로** 올려, 자동 추첨 체크박스와 추가 신청일
양쪽이 같은 값을 참조한다는 것이 시각적으로 드러나게 한다. 컬럼명은
`extra_request_*` 그대로 두되(마이그레이션 불필요), 화면 라벨만 '대상 분기'
로 바꾼다.

**동작 규칙**:

- `extra_request_year` / `extra_request_quarter` 가 비어 있으면 자동 추첨을
  **건너뛰고** 배너로 알린다 — `"대상 분기가 지정되지 않아 자동 추첨을
  건너뜁니다. 설정에서 대상 분기를 지정하세요."` 추측해서 돌리지 않는다.
- 관리자는 분기마다 이 값을 갱신한다. 마감일을 새로 잡을 때 함께 바꾸는
  것이 자연스러운 운용이다.

> **컬럼명과 화면 라벨이 어긋나는 점**은 감수한다. 이름을 바꾸려면 컬럼
> 이관과 `user-calendar.tsx` 수정이 따라오는데, 그 비용에 비해 얻는 것이
> 적다. 대신 `migrations.sql` 의 해당 섹션 주석에 "자동 추첨도 이 값을
> 대상 분기로 쓴다" 는 한 줄을 추가해 둔다.

### 3. 새 모듈 — `lib/auto-lottery.ts`

추첨 로직이 현재 재사용 불가능한 상태다. `drawIds()` 가
[admin-calendar.tsx:100-115](../components/admin-calendar.tsx#L100-L115) 의
**모듈 스코프 비공개 함수**라 다른 곳에서 import 할 수 없다. 공용 모듈로 꺼낸다.

```
lib/auto-lottery.ts
├─ drawIds(pool, cap)              ← admin-calendar.tsx:100-115 에서 이동 (export)
├─ collectBulkTargets(...)          ← admin-calendar.tsx:212-240 의 bulkTargets 로직 추출
├─ resolveTargetQuarter(settings)   ← 위 분기 판정 규칙
├─ runAutoLottery(...)              ← 분기 전체 조회 → 추첨 → UPDATE → 결과 반환
└─ buildResultDocument(results)     ← 게시할 제목/본문 텍스트 생성
```

`admin-calendar.tsx` 는 이 모듈에서 import 해 쓰도록 바꾼다.
**기존 개별 추첨·월 일괄 추첨의 동작은 그대로 유지한다 — 로직을 옮기기만 하고
바꾸지 않는다.** (그래서 검증 항목에 회귀 확인이 들어간다.)

재사용할 기존 유틸 — 새로 만들지 않는다:

| 유틸 | 위치 |
|---|---|
| `getPositionCap(date, holidays, caps)` | [schedule-utils.ts:106-116](../lib/schedule-utils.ts#L106-L116) |
| `countJigeunSlots(entries)` | [schedule-utils.ts:138-145](../lib/schedule-utils.ts#L138-L145) |
| `quarterRange` / `quarterMonths` | [lib/quarter.ts](../lib/quarter.ts) |
| `POSITIONS` | [lib/types.ts](../lib/types.ts) |

### 4. 추첨 실행 흐름

기존 `runBulkLottery()` 와 동일한 패턴을 분기 범위로 확장한 것이다.

1. 대상 분기의 `special_schedules` 조회(`lottery_status`, `staff_position` 포함)
   + `holidays` + `app_settings` caps
2. 날짜별로 묶어 (날짜 × 직책) 정원 초과 조합 수집
   - **이미 `lottery_status` 가 있는 조합은 제외** — 관리자가 손으로 돌린 결과를
     자동 실행이 뒤집으면 안 된다. 기존 일괄 추첨과 동일한 안전장치다.
3. 각 대상에 `drawIds()` 적용, won/lost id 전부 누적
4. `.in("id", allWon)` / `.in("id", allLost)` 두 번의 UPDATE
5. 성공 시에만 결과 문서 게시
6. 그 다음 `auto_lottery_done_for` 기록

**순서가 중요하다.** 문서 게시가 실패하면 `done_for` 를 남기지 않아 다음 접속
때 재시도한다. 이때 추첨은 이미 `lottery_status` 가 찍혀 2단계에서 제외되므로
**재추첨되지 않고 문서 게시만 재시도**된다 — 자연스럽게 올바른 재개 동작이 된다.

**알려진 비원자성**: 두 UPDATE 는 한 트랜잭션이 아니다. 기존 코드도 이를
주석으로 인정하고 있다([admin-calendar.tsx:592-596](../components/admin-calendar.tsx#L592-L596)).
자동 실행에서는 사람이 즉시 보지 못하므로 더 위험하다. → **실패 시
`auto_lottery_done_for` 를 기록하지 않고** 빨간 배너로
"일부만 반영되었을 수 있음 — 날짜별 확인 필요" 를 띄운다.

### 5. 결과 문서 게시

`documents` 테이블은 `file_url` 이 NULL 허용이고, 마이그레이션 주석이
"파일 없이 제목+설명만으로도 문서 게시 가능" 을 명시하고 있다. 그대로 활용한다.

```
제목: 2026년 3분기 지근 추첨 결과

본문:
2026-07-01 ~ 2026-09-30 지근 신청 추첨 결과입니다.
(자동 추첨 · 2026-06-16 실행)

■ 2026-07-05 기관사 (정원 4)
  당첨: 김OO, 이OO, 박OO, 최OO
  탈락: 정OO

■ 2026-07-12 차장 (정원 2)
  당첨: 김OO, 이OO
  탈락: 박OO, 최OO

...

※ 탈락하신 분은 추가 신청 기간(~2026-06-30)에
   다른 날짜로 재신청하실 수 있습니다.
```

- **명단 공개 범위**: 당첨자·탈락자 **전체 실명 공개**. 추첨의 투명성이 확보되고
  이의 제기가 쉬워진다.
- 이름은 `coworker_list` 를 `staff_id` 로 별도 조회해 매핑 —
  [lottery-losers-panel.tsx:176-200](../components/admin-panels/lottery-losers-panel.tsx#L176-L200)
  과 동일 관례(FK 임베딩 안 씀).
- 추가 신청 안내 문구는 `extra_request_deadline` 이 설정된 경우에만 붙인다.
- insert: `file_url: null`, `file_name: null`, `is_required: false`
  (열람 확인 의무 문서가 아니라 공유 목적. 필요하면 관리자가 문서 패널에서 수정).
- `created_by`: 자동 실행을 트리거한 로그인 관리자의 `staff_id`.

체크박스는 **마감일 바로 아래**에 둔다 — 마감일의 후속 동작이므로 인과가

## 검증 방법

**1. 마이그레이션 적용**
Supabase SQL Editor 에서 새 섹션 실행 후 확인:
```sql
select auto_lottery_enabled, auto_lottery_done_for,
       extra_request_year, extra_request_quarter, extra_request_deadline
  from app_settings where id = 1;
```
기존 `extra_request_*` 값이 **그대로 보존**되는지 확인한다(이관이 없으므로
변할 이유가 없지만, 새 섹션이 기존 컬럼을 건드리지 않았음을 확인하는 의미).

**2. 기존 동작 회귀 확인** (로직 이동이 있으므로 필수)
`npm run dev` → 관리자 → 내 캘린더:
- 개별 `추첨`/`재추첨` 버튼이 기존과 동일하게 동작
- 월 `일괄 추첨 (N)` 의 대상 건수와 실행 결과가 기존과 동일
- 자동 추첨이 꺼진 기본 상태에서는 배너도 뜨지 않고 아무것도 실행되지 않음

**3. 자동 실행 — 정상 경로**
- 설정에서 **대상 분기**를 정원 초과 신청이 있는 분기로, 마감일을
  **어제 날짜**로 지정하고 자동 추첨 체크
- 관리자 대시보드 새로고침 → 실행 중 배너 → 완료 요약
- `추첨 탈락자` 패널에서 해당 분기 탈락자 명단 생성 확인
- 사용자 계정으로 로그인 → `문서` 탭에 결과 문서가 보이고 본문의 당첨/탈락
  명단이 실제 DB 와 일치하는지 확인

**4. 대상 분기 — 일정과 대상 분기가 어긋나는 실제 운영 조건**
마감일이 어디에 있든 **대상 분기 설정값만** 따라가는지가 핵심이다.
대상 분기를 **3분기**로 고정하고 마감일만 바꿔 가며 확인한다:

| 마감일 | 신청 시점 | 기대 동작 |
|---|---|---|
| 5월 말 | 두 달 전 | 3분기를 추첨 |
| 6월 말 | 한 달 전 | 3분기를 추첨 |
| 6/30 | 분기 경계 직전 | 3분기를 추첨 |
| 7/1 | 분기 시작 후(예외 운영) | 3분기를 추첨 |

- 네 경우 모두 **2분기를 건드리면 실패**다. 마감일 위치와 무관하게 결과가
  같아야 한다 — 어떤 형태로든 날짜에서 분기를 계산하고 있다는 뜻이 되므로.
- 대상 분기를 비운 상태로 실행 → **아무것도 실행되지 않고** "대상 분기가
  지정되지 않았습니다" 배너만 뜨는지 확인

**5. 검증 완화 — 설정 저장 조합** (이번 변경의 핵심 영향 범위)
[jigeun-cap-settings.tsx:177-198](../components/jigeun-cap-settings.tsx#L177-L198)
의 검증을 푸는 것이므로 네 조합을 모두 확인한다:

| 추가 신청일 | 연도·분기 | 기대 |
|---|---|---|
| 있음 | 있음 | 저장됨 (현행 유지) |
| 없음 | **있음** | **저장됨** ← 이번에 새로 허용. 추가 신청은 닫히고 자동 추첨만 동작 |
| 있음 | 없음 | 에러 "년·분기도 함께 지정하세요" (현행 유지) |
| 없음 | 없음 | 저장됨 (현행 유지) |

- 두 번째 조합으로 저장한 뒤 **사용자 화면에서 추가 신청이 닫혀 있는지**
  확인한다(`extra_request_deadline` 이 NULL 이므로 `inExtraWindow` 가 false).
- 그 상태에서 자동 추첨이 정상 동작하는지 확인한다.
- 기존처럼 세 값을 모두 채운 분기에서 **추가 신청이 종전과 똑같이**
  동작하는지 확인한다(탈락 이력 있는 직원은 열리고, 없는 직원은 닫힘).

**6. 멱등성**
- 대시보드를 여러 번 새로고침 → 두 번째부터는 실행되지 않고 문서도 추가
  게시되지 않음 (`auto_lottery_done_for` 확인)
- 마감일을 다른 날짜로 바꾸면 다시 실행되는지 확인

**7. 기존 추첨 보존**
- 일부 날짜를 손으로 먼저 추첨해 둔 뒤 자동 실행 → 그 날짜의 당첨자가
  **바뀌지 않고** 문서에도 기존 결과가 그대로 반영되는지 확인

**8. 실패 복구**
- 문서 게시 단계를 의도적으로 실패시켰을 때(예: 네트워크 차단)
  `auto_lottery_done_for` 가 기록되지 않고, 다음 새로고침에서 **재추첨 없이
  문서 게시만** 재시도되는지 확인

## 미결 사항

구현을 결정할 때 함께 정해야 할 것들:

- **컬럼명(`extra_request_*`)과 화면 라벨('대상 분기')의 불일치** —
  기존 컬럼을 그대로 쓰기로 하면서 생긴 부채다. 이름을 맞추려면 컬럼 이관과
  `user-calendar.tsx` 수정이 따라오는데, 그 비용에 비해 얻는 것이 적어
  감수하기로 했다. 다만 나중에 이 코드를 읽는 사람이 혼동할 수 있으므로
  `migrations.sql` 섹션 21 주석에 용도를 한 줄 덧붙여 둔다.
  자동 추첨 외에 이 값을 참조하는 기능이 더 늘어나면 그때 이름 변경을 재검토한다.
- **대상 분기를 관리자 화면 헤더에 표시할 것인가** — 헤더에는 이미 마감·추가
  배지가 있다([admin-dashboard.tsx:129-152](../components/admin-dashboard.tsx#L129-L152)).
  "지금 어느 분기를 처리 중인가" 가 자동 추첨의 전제가 되므로 배지를 하나 더
  두는 편이 안전하지만, 헤더가 좁아지는 문제가 있다.
- **관리자 승인 단계를 둘 것인가** — 지금 설계는 조건이 맞으면 바로 실행한다.
  대신 "마감일이 지났고 미추첨 N건이 있습니다 [지금 추첨]" 배너만 띄우고
  클릭을 받는 방식도 가능하다. 개입이 1클릭 늘지만 사고 위험은 준다.
- **문서 게시 후 알림** — 현재 `documents` 는 사용자가 문서 탭을 열어야 본다.
  `is_required: true` 로 열람 확인을 강제하거나 `announcements` 에 짧은
  안내를 함께 올리는 선택지가 있다.
- **B(pg_cron) 로의 승격 시점** — 승무소가 늘거나 관리자 접속 빈도가 낮아지면
  A 의 한계가 드러난다. 그때 재검토.
